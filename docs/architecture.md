# Бэкенд — архитектура

Источник правил: `skeleton/02-backend.md`, `04-configs.md`,
`05-arch-checks.md`. Этот файл — рабочая копия для проекта **Areve**; при
расхождении с новым решением правится он, а не скелет.

Проект: лендинг центра детской занятости **Արևէ** (Areve), Абовян.
Состав модулей — раздел 10.

---

## 1. Стек

| Что | Чем |
|---|---|
| Язык | TypeScript, **CommonJS** (`module: node16`) |

## 2. Модульный монолит

Одна служба, но модули устроены как будущие сервисы: **любой можно выделить в
отдельный процесс, не переписывая потребителей.**

```
server.ts  →  app/app.ts  →  роутеры модулей
```

### Дерево

```
areve-backend/
  docs/                          architecture.md, model.md, project-plan.md, UI-fixes.md
  tests/                         договор с фронтендом
  skeleton/                      правила архитектуры
  tsconfig.json  eslint.config.mjs  .env.example
  prisma/schema.prisma  prisma/migrations/
  tools/check-architecture.cjs   машинная проверка архитектуры
  src/
    server.ts       вход: проверка env, запуск HTTP
    app/app.ts      сборка Express: middleware и роутеры модулей
    modules/        предметные области
      <name>/
    shared/         общее, не знающее о предметных областях
      config/       logger, prisma, mailer
      errors/       AppError, коды ошибок
      http/         asyncHandler, errorHandler, requestLogger,
                    handleValidationErrors, param
      lib/          чистые помощники
      types/        расширение типов Express
    scripts/        разовые скрипты обслуживания
```

## 3. Устройство модуля

| Файл | Что кладём |
|---|---|
| `<name>.routes.ts` | маршруты, подключение валидаторов |
| `<name>.controller.ts` | разбор запроса, HTTP-статус, ответ |
| `<name>.service.ts` | предметная логика и запросы Prisma |
| `<name>.validation.ts` | валидаторы express-validator |
| `<name>.notification.ts` | что и кому сообщить о событии модуля |
| `index.ts` | публичный API модуля |

`notification` — добавление к списку из скелета. Появилось, когда о новой
заявке понадобилось слать письмо: **что** отправить решает модуль, **как**
отправить — `shared/config/mailer`, который о заявках не знает.

- **Контроллеры не обращаются к Prisma.**
- **Сервисы не знают про `req`/`res`.**
- Контроллер выбрасывает `AppError`, а не пишет `res.status(4xx)`.
- Статичные пути объявляются **до** `/:id`.

Готовый пример модуля — `02-backend.md`, раздел 4.

## 4. Правила зависимостей

- **`shared` не знает ни о модулях, ни о приложении.**
- **В чужой модуль — только через его `index.ts`.** Экспорт добавляется, когда
  понадобился, а не впрок.
- **Внутри своего модуля — относительные пути к своим файлам**, не через свой `index.ts`.
- **Модули не образуют кругов.** Общая часть двух модулей переезжает в модуль,
  от которого зависят оба.
- **`app/` и `server.ts` берут у модулей только публичный API**; их самих никто
  не импортирует.
- **Модуль не читает чужие таблицы напрямую** — только через сервис модуля-владельца.
- **Импорты — относительными путями.** Псевдоним `@/` `tsc` при сборке не переписывает.

## 5. Порядок middleware

Порядок в `app/app.ts` строгий:

| № | Что | Почему так |
|---|---|---|
| 0 | `requestLogger` | первым — чтобы в лог попали и отказы CORS |
| 1 | `helmet()` | заголовки безопасности |
| 2 | `cors(...)` | до маршрутов; список из `CORS_ORIGINS` |
| 3 | `express.json`, `express.urlencoded` | лимит `1mb` |
| 4 | роутеры модулей | `app.use("/api/<name>", <name>Routes)` |
| 5 | `notFoundHandler` | |
| 6 | `errorHandler` | единственное место, где ошибка становится ответом |

Запрос без `origin` (curl, server-to-server) CORS пропускает.
`X-Request-Id` отдаётся наружу через `exposedHeaders`.

## 6. Ошибки

Все ошибки — одним конвертом:

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "…", "details": [] } }
```

- `code` — машинный идентификатор, по нему фронтенд подставляет перевод.
- `details` есть только у валидации и **не содержит введённых значений**.
- Базовые коды: `VALIDATION_FAILED`, `NOT_FOUND`, `CONFLICT`, `INTERNAL`.

Правила:

- Новый код заводится, **когда пользователь должен действовать иначе**.
- Каждый новый код получает перевод в разделе `errors` фронтенда — в той же правке.
- `AppError` — то, что безопасно показать. Всё остальное наружу уходит как
  `INTERNAL` без подробностей: в тексте исключения бывают параметры запроса к БД.
- Оригинальный текст ошибки стороннего middleware (битый JSON, большое тело) —
  только в лог; наружу общая формулировка.
- В `development` к `INTERNAL` добавляется `details` со стеком.

## 7. Логирование

`pino` вместо `console`. Единственное исключение — проверка env в `server.ts`:
в dev pino пишет асинхронно, и при немедленном `exit` сообщение не успевает выйти.

- У каждого запроса идентификатор: из `X-Request-Id`, если пришёл от прокси,
  иначе генерируется; возвращается в ответе и попадает в каждую запись лога.
- Уровень: 5xx — `error`, 4xx — `warn`, остальное — `info`.
- Цепочка `cause` обрезается до типа и сообщения — там бывают тексты SQL с аргументами.
- `LOG_LEVEL` из окружения; в dev — `debug` и `pino-pretty`.

## 9. Проверка архитектуры

`npm run check:arch` → `tools/check-architecture.cjs` (скрипт целиком — `05-arch-checks.md`).

Ловит: файлы вне `server.ts` / `app/` / `modules/` / `shared/` / `scripts/`;
импорт `app` или `server.ts` кем-либо кроме них; `shared` → модули/приложение;
обход чужого `index.ts`; свой модуль через собственный `index.ts`;
**круги между модулями**. В конце печатает граф зависимостей модулей.

**Зелёный результат обязателен для каждой правки.** Дополнительно на pre-commit:
`lint-staged` (eslint --fix) и `tsc --noEmit`.

## 10. Модули проекта Areve

### Что делает сервер

Сайт — лендинг. Весь контент статичен и живёт во фронтенде. Сервер нужен ровно
для одного: **принять заявку из формы обратной связи** (имя, телефон,
сообщение) и сохранить её, чтобы центр мог перезвонить.

### Состав

| Модуль | Отвечает за | Таблицы |
|---|---|---|
| `leads` | приём и хранение заявок | `Lead` |

Один модуль. Граф зависимостей, который печатает `check:arch`, будет пустым —
это правильное состояние, а не признак недоделанности.

```
POST /api/leads      создать заявку      201 + { id }
GET  /api/health     проверка живости    200 + { status: "ok" }
```

`/api/health` — не модуль, а два десятка символов в `app/app.ts`: маршрут без
предметной логики, нужен хостингу и мониторингу.

### Замечание о соразмерности

Модульный монолит с Prisma и PostgreSQL ради одной таблицы с заявками — это
заметно больше механики, чем требует задача. Разумные альтернативы существуют:
отправлять заявку письмом или в Telegram без базы вовсе.

Архитектура при этом остаётся выбранной: скелет готов, проверки работают,
и когда у центра появится вторая задача (расписание, группы, личный кабинет
родителя) — место под неё уже есть. Просто не нужно раздувать `leads` работой,
которой у него нет.

### Чего в проекте не будет

Авторизации, ролей, оплаты, загрузки файлов. Всё это в скелете отсутствует
и потребует отдельного решения.

**Исключение, о котором стоит подумать заранее:** если центру нужна страница со
списком заявок, а не только письмо на почту — это уже авторизация. Пока
считаем, что заявки уходят уведомлением, а не читаются через сайт.

### Что нужно добавить сверх скелета

Форма открыта всему интернету без авторизации, поэтому:

1. **Ограничение частоты запросов** на `POST /api/leads` — по IP, с запасом
   (несколько заявок в час на адрес). В скелете этого нет.
2. **Ловушка для ботов** — скрытое поле, которое человек не заполняет;
   заполнено → ответ 201, запись не создаётся.
3. **Код ошибки `RATE_LIMITED`** в `ErrorCode` + перевод на фронтенде.
4. **Уведомление о новой заявке** — ✅ сделано 18.09.2026.
   **Решено: письмо на рабочий Gmail центра, отправляет сервер.**
   Вариант с `mailto:` из обновлённого лендинга отклонён — он теряет заявку
   молча, если у родителя не настроен почтовый клиент.

   Устройство: `shared/config/mailer` (SMTP, ничего не знает о заявках) +
   `modules/leads/leads.notification.ts` (текст письма). Вызывается из сервиса
   **без `await`**: заявка уже в базе, и ответ не ждёт почтовый сервер.
   Упавшая отправка — запись в лог, а не отказ формы.

   Для Gmail нужен **пароль приложения**, а не пароль от почты: обычный пароль
   SMTP не пропустит. Создаётся в настройках аккаунта Google при включённой
   двухэтапной проверке.

### Персональные данные

В `Lead` попадают имя и телефон родителя. Отсюда:

- **Телефон и имя не пишутся в логи** — ни в `requestLogger`, ни в тексте ошибок.
  Тело `POST /api/leads` логировать нельзя.
- В `details` ошибки валидации уходит только имя поля, без значения — так уже
  устроен `handleValidationErrors` в скелете.
- Нужен срок хранения заявок и процедура удаления — решается с центром.
- На сайте нужна страница или блок о том, как обрабатываются данные.
